# Instamart Customer Copilot

## 1. Overview

The Instamart Customer Copilot project builds a data-driven customer analytics and support automation system using Python, Pandas, NumPy, SQLite, Scikit-learn and a simulated LLM.

The project is divided into four parts:

- **Part A – Data Pipeline, SQL Analysis and EDA:** Audits and cleans raw customer, product and order data, stores the cleaned data in SQLite, performs SQL analysis and validates results using Pandas.
- **Part B – Customer Segmentation and Lapse Prediction:** Calculates RFM metrics, identifies customer segments using K-Means clustering and builds machine-learning models to predict customer lapse.
- **Part C – Support Ticket Triage with Guardrails:** Processes support tickets with privacy protection, input validation, retry handling, output validation, token-budget controls and customer-aware routing.
- **Part D – Policy RAG Assistant and Refund Agent:** Implements policy retrieval using TF-IDF and a tool-calling ReAct agent to process refund requests with safeguards and checkpoint-based recovery.

All LLM interactions use the supplied `mock_llm.py`. No external API key or real network-based model call is required.

### 3.3 Order Data Cleaning

Order cleaning follows the required sequence:

1. Convert `order_ts` into datetime format.
2. Remove exact duplicate records.
3. Sort by order timestamp and retain the latest record for each `order_id`.
4. Convert `order_amount` into numeric values.
5. Calculate missing or invalid order amounts using:

   `price_inr × quantity × (1 - discount_pct / 100)`

   The calculated amount is rounded to two decimal places.

6. Convert delivery times into numeric values and replace negative values with missing values.
7. Impute missing delivery times for completed orders using the product-category median calculated from completed orders.
8. Keep missing delivery times for cancelled orders.
9. Format timestamps as `YYYY-MM-DD HH:MM:SS`.

### 5.3 Zero-Shot and Few-Shot Prompts

Two system prompts are used:

- **Zero-shot:** Instructs the model to classify tickets into the four allowed categories and return JSON only.
- **Few-shot:** Includes an `EXAMPLES:` section with labelled examples, including a fraud example, before the same classification instructions.

Both prompts contain the word `CLASSIFY`, list the categories `billing`, `delivery`, `technical` and `fraud`, and require a JSON response in this format:

```json
{
  "category": "...",
  "reason": "..."
}
```

### 5.4 Retry Mechanism

Every model call is wrapped in retry handling for `TransientLLMError`.

The retry configuration is:

- Maximum retries: 3.
- Base delay: 0.05 seconds.
- Exponential backoff with jitter:

  `BASE_DELAY × 2**n × random.uniform(0.9, 1.15)`

Each retry produces a log entry containing the ticket ID, retry number and wait duration.

`mock_llm.reset()` is called immediately before each full run.

Across a full run, 19 transient errors are encountered and all 19 are recovered. No eligible ticket ends with a permanent model-call error.

### 5.5 Output Validation

Model responses are validated using two methods.

1. Valid JSON is accepted when its category belongs to the four allowed categories. The status becomes `classified_json`.
2. If the response is not valid JSON, lowercase words are extracted using `re.findall(r"[a-z]+", text.lower())`. The response is accepted only when exactly one allowed category word is found. The status becomes `classified_keyword`.

All other responses, including valid JSON with an unsupported category, are marked `flagged_invalid_output` and routed to human review.

Automatically classified tickets are rule-validated before routing. Empty, long and invalid-output tickets are not automatically assigned a category and are sent to human review.

## 6. Part D – Policy RAG Assistant and Refund Agent

### 6.1 Policy Document Chunking

The policy assistant reads five text documents from `data/policies/`.

Each document is divided into chunks of 40 words with an overlap of 10 words. The next chunk starts 30 words after the previous chunk starts.

Each chunk retains its source filename.

| Policy Document | Chunks |
|---|---:|
| refund_policy.txt | 4 |
| delivery_policy.txt | 3 |
| escalation_policy.txt | 3 |
| payment_policy.txt | 3 |
| privacy_policy.txt | 2 |
| **Total** | **15** |

Overlapping chunks help retain information that might otherwise be separated at a chunk boundary.

### 6.2 TF-IDF Vectorization and Retrieval

The chunk texts are vectorized using Scikit-learn's `TfidfVectorizer()`.

The same fitted vectorizer transforms incoming queries. Cosine similarity is then used to rank chunks by relevance.

The retrieval function returns the top results with:

- Source filename
- Similarity score
- Chunk text

**TF-IDF explanation:**

Term Frequency (TF) measures how often a term appears in a document or chunk. Inverse Document Frequency (IDF) reduces the weight of terms that occur frequently across many documents, helping distinctive terms contribute more to relevance.

One limitation of TF-IDF is that it relies on word overlap rather than understanding meaning. Two questions with similar meanings but different wording may receive low similarity scores even when the relevant policy information exists.

For the query `refund policy late delivery`, the top three retrieved chunks all come from `refund_policy.txt`, matching the expected retrieval result.

### 6.3 Retrieval-Augmented Policy Answering

The `answer(question)` function:

1. Retrieves the three most relevant policy chunks.
2. Builds a system message containing `POLICY ASSISTANT`.
3. Instructs the model to answer only from the supplied context.
4. Requires the model to say `I could not find` when the context does not contain the answer.
5. Sends the context and question in the required format.
6. Returns the model answer and the sources used.

The user message follows this structure:

```text
CONTEXT:
[policy_source_1.txt]
First retrieved chunk

[policy_source_2.txt]
Second retrieved chunk

[policy_source_3.txt]
Third retrieved chunk

QUESTION:
User question
```

The assistant uses the retrieved policy context rather than relying on unsupported general knowledge.

### 6.4 Retrieval and Grounding Evaluation

The retrieval pipeline is evaluated using the 14 questions in `data/raw/policy_eval.csv`.

Twelve questions are answerable using the policy documents, and two are not covered by the documents.

**Normal overlap evaluation:**

| Evaluation | Result |
|---|---:|
| Expected document in top three | 12/12 |
| Expected fact in answer | 12/12 |
| Unanswerable questions using fallback | 2/2 |

The normal overlapping chunks retrieve the required policy information and support all answerable questions.

**Zero-overlap evaluation:**

The documents are processed again using 40-word chunks with no overlap.

| Evaluation | Result |
|---|---:|
| Total chunks | 13 |
| Expected document in top three | 12/12 |
| Expected fact in answer | 10/12 |
| Unanswerable questions using fallback | 2/2 |

Two questions fail to return the expected facts:

1. **Refund eligibility:** The question asks what delivery time makes a completed order eligible for a full refund. The generated answer includes the full-refund statement but does not include the exact expected fact `more than 45 minutes`.
2. **Failed payment:** The question asks how soon money is returned when a payment fails but is deducted. The generated answer does not contain the expected fact `48 hours`.

These failures demonstrate how zero-overlap chunking can separate related information across chunk boundaries. A retrieved chunk may contain part of the answer without containing the full fact needed to answer the question.

The overlapping configuration therefore provides better grounding for this policy dataset.

### 6.5 Refund Tools and Tool Map

The refund agent uses five tools, each with a name, description and JSON-style parameter specification in `TOOLS_SPEC`.

The `TOOL_MAP` connects each tool name to its Python function.

| Tool | Purpose |
|---|---|
| `get_order` | Retrieves order details from the SQLite database. |
| `search_policy` | Retrieves relevant policy chunks. |
| `calculate_refund` | Calculates the refund according to the policy rules. |
| `issue_refund` | Records an approved automatic refund in the ledger. |
| `escalate_to_human` | Records a refund requiring human approval. |

**Refund rules:**

- Only completed orders are eligible for refunds.
- Completed orders delivered in more than 45 minutes qualify for a full refund.
- Completed orders delivered in 45 minutes or less receive no late-delivery refund.
- Refunds above INR 1,000 must be escalated to a human support lead.
- Cancelled orders are not eligible for refunds.
- All simulated requests are treated as being raised within the policy's seven-day window.
- The refund issuance and escalation functions also validate order status before recording the action, preventing cancelled orders from receiving refunds.

The `get_order` tool reads the order from `data/instamart.db`. If an order does not exist, it returns:

```json
{
  "error": "order not found"
}
```

The `search_policy` tool returns retrieval results under the `results` key.

The `calculate_refund` tool returns the calculated amount under `refund_inr`.

The `issue_refund` and `escalate_to_human` tools append JSON records containing a timestamp and tool name to `outputs/refund_ledger.jsonl`.

### 6.6 ReAct Agent Workflow

The refund agent implements a ReAct (Reasoning and Acting) loop using `mock_llm.chat()`.

The agent starts with a system message containing `AGENT` and the user's request.

During each iteration:

1. The model receives the current conversation and decides whether a tool is needed.
2. If a tool call is returned, the assistant tool-call message is appended.
3. The tool name is looked up in `TOOL_MAP`.
4. The corresponding Python function is executed using the supplied arguments.
5. The tool result is appended as a JSON-formatted tool message.
6. The agent continues until a final answer or a safeguard is reached.

The agent returns:

- `status`
- `final_answer`
- `steps`
- `llm_calls`
- `tokens_used`

The status is extracted from the final answer for normal outcomes.

### 6.8 Safeguards and Fallbacks

The agent enforces three safeguards.

**Maximum iteration limit**

The agent stops when it reaches the configured maximum number of model calls without a final answer.

S7 ends with:

`FALLBACK_MAX_ITERATIONS`

**Token limit**

After each model response, the agent adds `usage.total_tokens` to the running total. If the total exceeds the configured limit, it stops before executing the tool requested in that response.

The S1 demonstration uses a token limit of 200.

Result:

`FALLBACK_TOKEN_LIMIT`

The agent stops when the cumulative token count exceeds the configured limit, before executing the requested tool.

**Timeout**

The agent checks elapsed time at the start of every iteration using `time.monotonic()`.

When the elapsed time is greater than or equal to the configured limit, the agent stops and returns a human-handoff summary.

The S1 timeout demonstration uses `time_limit_seconds=0`.

Result:

`FALLBACK_TIMEOUT`

The demonstration stops before the first model call, with zero calls and zero tokens.

### 6.9 Checkpointing and Crash Recovery

After every tool observation is appended, the agent saves a checkpoint in `state/`.

Each checkpoint contains:

- Run ID
- Scenario ID
- Full message history
- Tokens used
- Step number
- Tools already executed

The `resume_agent(run_id)` function loads the checkpoint and continues from the saved state.

The crash-and-resume demonstration uses S1. A simulated crash occurs immediately after the second tool execution, after the checkpoint has been saved.

**Tool execution order across both runs:**

1. `get_order`
2. `search_policy`
3. `calculate_refund`
4. `issue_refund`

There are exactly four tool executions across the crash and resumed run, with no repeated tool execution.

The resumed agent completes successfully:

`REFUND: INR 128.25 issued.`

### 6.10 ReAct versus Plan-and-Execute

ReAct makes decisions iteratively, allowing the agent to inspect each tool observation before deciding what to do next. In the measured scenarios, S1 requires five model calls, S5 requires three and S6 requires two. This increases model-call and token usage compared with a plan-and-execute approach that requests the full action plan in one call and replans only when an error occurs.

Plan-and-execute can be more efficient for predictable requests because it reduces the number of model calls. However, it may need additional replanning when an unexpected observation occurs, such as an order returning `NOT_FOUND`, a cancelled order or a refund requiring human approval.

For this refund workflow, ReAct is preferred because each tool result can influence the next action. It allows the agent to verify the order, retrieve the policy, calculate the refund and then decide whether to issue or escalate it. The additional model calls provide better control and adaptability for financial actions where incorrect execution could cause problems.

## 7. Limitations and Next Steps

### Limitations

- The project uses a simulated LLM through `mock_llm.py`, so the results do not represent the behaviour of a live production LLM.
- TF-IDF retrieval relies on lexical similarity and may miss semantically related policy questions with different wording.
- Zero-overlap chunking demonstrates that policy facts can be split across chunk boundaries, reducing answer grounding.
- The lapse model is trained and evaluated on a single generated dataset and may not generalize to real customer behaviour.
- The Premium retention list is illustrative because its segment membership uses the full September RFM window, which overlaps with the lapse-label period.
- The refund ledger and checkpoint files simulate tool execution and recovery; they are not connected to an actual payment or support system.
- The model-selection results are based on the supplied assignment dataset and should be validated on additional unseen data before production use.

### Next Steps

- Evaluate the customer segmentation and lapse prediction models on newer customer and order data.
- Monitor model precision and recall as customer behaviour changes.
- Explore semantic embeddings or hybrid retrieval to improve policy search.
- Add stronger production-level validation and audit logging for tool execution.
- Integrate refund approval with an authenticated payment and support system.
- Add monitoring for token usage, failed model calls and human-review workloads.
- Validate the complete workflow using a clean environment and additional test datasets.

The Instamart Customer Copilot combines data engineering, SQL analytics, customer segmentation, lapse prediction, guarded support-ticket classification and retrieval-grounded refund automation. The four parts demonstrate how customer data and policy information can be used to support customer retention, improve ticket routing and automate eligible refund decisions while maintaining validation, privacy and recovery safeguards.
